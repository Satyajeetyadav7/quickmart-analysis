**Live dashboard:** `https://YOUR-APP-NAME.streamlit.app` &nbsp;|&nbsp; **Stack:** Python · SQL (SQLite) · pandas · scikit-learn · Plotly · Streamlit

> End-to-end analytics project on a **simulated Indian quick-commerce business** (Blinkit / Zepto / Instamart style).
> It answers the questions a growth or business analyst is asked every week: *Who are our best customers? Who is about to

## Business problem

A quick-commerce company is growing fast but burning cash on discounts and paid acquisition. Leadership wants to know where
growth is healthy, where money is wasted, and which customers to save before they churn.

## What is inside

- **SQL (9 queries in `sql/queries/`)**: CTEs, `LAG`/`LEAD`, `NTILE`, `RANK`, `SUM() OVER`, conditional aggregation, cohort date math,
  right-censoring-aware repeat-rate logic, LTV:CAC unit economics.
- **Data engineering**: a normalised SQLite schema with keys and indexes (`sql/schema.sql`) and 8 automated data-quality checks
  (orphans, impossible values, order-total reconciliation, etc.).
- **Churn model** (`src/churn_model.py`): features built as-of a snapshot date (no leakage), **out-of-time validation**, logistic
  regression vs gradient boosting, permutation importance, and a scored win-back list.
- **Dashboard** (`app.py`): 7 views with live filters, downloadable CSV lists, and a read-only **SQL lab** where visitors can run their own queries.

## Run it locally

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate      Mac/Linux: source .venv/bin/activate
pip install -r requirements.txt

python -m src.run_pipeline      # optional: regenerates data, DB, query results, churn model (~15 s)
streamlit run app.py            # opens http://localhost:8501
```

The app rebuilds the database automatically if `data/quickcart.db` is missing.

## Method notes and honest limitations

- **Data is simulated.** No real company data was used. `src/generate_data.py` bakes in plausible behaviour (slow deliveries and
  cancellations reduce repeat orders, deal-seekers churn faster, festive spikes, seasonal categories), so the findings show that the
  *analysis pipeline works*, not facts about a real business. Swap in a real dataset by loading it into the same schema.
- **CAC is assumed** (`channel_cac` table), and "gross profit" excludes delivery, rider and dark-store costs.
- **Discount analysis is observational.** Customers who receive deep discounts are not randomly chosen, so the next step before
  changing policy would be an A/B test.
- **Repeat rate ignores the last 30 days of data** so every order has a full 30-day window (right-censoring).
- **RFM scores use `NTILE`**, which splits ties arbitrarily; fine for segmentation, but note it when explaining the method.
- Logistic regression slightly beat gradient boosting out-of-time (0.836 vs 0.825 AUC), so the simpler, more explainable model is used.
